# Decisions

| Date | Decision | Reason |
|---|---|---|
| 2026-11-18 | Collect all routes | Collection cost is the same, and data not collected cannot be recovered later |
| 2026-11-18 | Poll vehicle positions and trip updates every 20 s, alerts every 5 min, around the clock | About 0.1% of the host's stated rate limit; off-hours responses are part of the record |
| 2026-11-18 | Collector on Supabase (scheduled edge function), pipeline and archive on GitHub | No server to run; sub-minute scheduling; no cost |
| 2026-11-18 | Store raw responses before parsing; treat them as the source of truth | Parsing can be redone; collection cannot |
| 2026-11-18 | Keep every field the feed sends, including `occupancy_status` | Full transparency; it is a per-vehicle category, not data about a person |
| 2026-11-18 | Publish raw and derived data from the first day | Visibility; data sits in Releases so it can be withdrawn if the agency objects |
| 2026-11-18 | Identify the collector by project name and repository URL in the User-Agent | Lets the host see who is polling and where to complain |
| 2026-11-18 | On-time window: 1 minute early to 5 minutes late, at true timepoints only | Common agency convention; Passio schedule times at other stops are interpolated |
| 2026-11-18 | One collector function for real-time and static downloads | Fewer parts to deploy than the two functions first planned |
| 2026-11-19 | Keep polling trip updates every 20 s although they refresh about once a minute | Cheap, and the refresh rate is itself something to measure; revisit after a week of data |
| 2026-11-19 | Limit prediction-error figures to trips matched to a reporting vehicle | The trip-update feed also lists upcoming trips that have no bus yet |
| 2026-11-19 | Use the feed's speed field to detect stationary buses | Present on every vehicle in the daytime check |
| 2026-11-19 | The collector checks its shared secret by asking the database, not from a function environment variable | Setup needs no manual step, and the secret never leaves the database |
| 2026-11-19 | Download the Passio static GTFS twice a day (2:15 AM and 8:30 AM Pacific) | The zip was incomplete at night and complete in the morning; sampling both times measures that |
| 2026-11-19 | Collection started 21:24:41 UTC | First logged fetch |
| 2026-11-19 | Archive complete Pacific days shortly after midnight, not the same evening | A day is not finished until midnight; off-hours fetches belong to it |
| 2026-11-19 | Collector version 0.2.0 from 21:37 UTC | Adds the prune step; fetching is unchanged |
| 2026-11-19 | Parsed tables store runs of unchanged values, not one row per fetch | Polling every 20 s repeats most values; runs keep every change and how long each value was seen, at a fraction of the size |
| 2026-11-19 | Parsed tables are built from the archived raw file, not from the collector | Every derived row then traces to a published file and its hash |
| 2026-11-19 | Parsed tables go to their own `parsed-YYYY-MM` releases, rebuilt when the table code version changes | Raw files never change; derived files can be regenerated |
| 2026-11-19 | Static GTFS versions are identified by the hash of every file except `feed_info.txt` | Passio rewrites its feed_info dates daily and Trillium stamps generation time; neither is a schedule change |
| 2026-11-19 | Each service day is pinned to the first complete download that day, else a matching incomplete download, else the latest earlier complete download | Uses the schedule as published for that day where possible, and records which rule applied |
| 2026-11-19 | Identify true timepoints by route and stop, not trip by trip | The Passio and Trillium schedules differ (route 1 weekdays: 68 trips from 03:35 in Passio, 43 from 03:45 in Trillium), so trips cannot be paired; how far they differ is reported as schedule agreement |
| 2026-11-19 | Stop crosswalk: same `stop_code` within 150 m, else nearest stop within 60 m | Codes match for most stops; a few shared codes point to stops kilometers apart; many NAS Whidbey stops have no code in Passio |
| 2026-11-19 | Quality metrics are written to the `data` branch as one JSON file per day plus a headline CSV | Small, diffable, readable by the site without a server |
| 2026-11-19 | Scheduled trips come from the Passio calendar even on holidays; Trillium's holiday removals are reported alongside | Passio is the schedule the real-time feed follows; mixing calendars would hide the disagreement |
| 2026-11-19 | Treat Passio as the schedule in effect; use Trillium only for timepoint flags, and check those against the published timetables | Island Transit's website timetable (effective 2026-09-27) matches Passio on the route 1 trips checked and not Trillium, whose calendar dates from 2025-06-01 |
| 2026-11-19 | Keep the printed timetable stops (service guides effective 2026-09-27) in `reference/` and check timepoints against them | They are the agency's published timepoints; the Trillium feed is out of date. 93% of matched printed timepoints are also Trillium timepoints |
| 2026-11-20 | True timepoints come from the printed timetables, not the Trillium feed (Davin's decision) | They are what the agency publishes; Trillium's schedule is out of date. Trillium's flags stay as a comparison. A new reference file is needed at each service change |
| 2026-11-20 | Printed timetable names that fit no single Passio stop are left out, not guessed | A wrong timepoint would put wrong numbers in on-time figures; the count of unresolved names is published daily |
| 2026-11-20 | Track a trip from the first position near its start, not the first position carrying its id | On loop routes the bus shows the next trip id while finishing the previous loop; anchoring on those positions misplaced whole trips |
| 2026-11-20 | Report stop events and on-time figures from the first day, labelled experimental | Visibility; the method and its limits are published, and field validation follows |
| 2026-11-20 | Quality metrics from stop events (`quality/0.2.0`): stop-level coverage, off-shape share, prediction error, unassignable trips, jitter, vehicles missing against 30 days | Methods listed them; stop events now exist. Labelled experimental with the events |
| 2026-11-20 | Predictions whose clock time falls on another Pacific day than the trip are counted separately and left out of prediction error | The feed sends no `start_date`; about 1 to 2% of short-horizon predictions on 2026-11-19 pointed at the next day's run of the same trip id, with errors of 6 to 19 hours that would swamp the means |
| 2026-11-20 | Place stops on shapes by ordered best fit over every pass, not nearest point ahead (`events/0.2.0`) | On loops a stop beside a road used again at the end of the loop was placed at the end, taking every later stop with it (routes 1C and 2C) |
| 2026-11-20 | Collapse shape segments drawn forth, back and forth again; report the meters removed | Passio's 1C shapes repeat every segment, making them 76 km for a 45-minute loop; distances along the shape were about three times the distance driven |
| 2026-11-20 | Let tracking move past parts of the shape a bus does not drive, once two consecutive positions agree; give those stops no time | 1C and 2C buses leave out loops that the published shapes include (for example Cama Beach and Russell Rd on 1C); before, tracking stopped there and the rest of the trip was lost |
| 2026-11-20 | Run validation checks 2 and 3 (feed stop-sequence agreement, segment travel times) every night and publish them beside the on-time figures | They need no field data, so the method's agreement with the feed is visible from day one; field timing (check 1) still decides when the experimental label comes off |
| 2026-11-20 | Several scheduled nightly attempts a day, a watchdog catch-up that dispatches the nightly job, and site deploys only when data changed | GitHub never started the first 08:35 UTC nightly run and fired the 30-minute watchdog only twice in its first day; every nightly step handles pending days only, so extra attempts are harmless |
| 2026-11-20 | Start the nightly archive and watchdog from pg_cron through GitHub's dispatch API, keeping the GitHub schedules as a fallback | GitHub skipped the first 08:35 UTC nightly run and fired the 30-minute watchdog once in about 12 slots; the first day was archived by a manual run at 09:10 UTC. pg_cron already runs the collector reliably. Costs nothing; needs a repository-only token in Vault |
| 2026-11-20 | Randomness of gaps (`quality/0.3.0`, `gaps/0.1.0`): store each day's trip-level coverage rows, publish rates from day one, fit a Firth logistic model from 14 days and 30 unobserved trips | Rates are descriptive and safe on little data; a model on one partial day (161 trips, 5 unobserved) would be noise. Firth's method because some routes will have no unobserved trips, where ordinary maximum likelihood gives infinite estimates. Hour bands instead of single hours keep the number of parameters small |
| 2026-11-20 | Field check: observers time the bus at 40 m before and 40 m past the stop, on sheets generated from the schedule with trip ids filled in; scored nightly | The same definition as the inferred times, so a difference measures the method, not a change of definition. Prefilled trip ids remove guessing which bus was which; scoring every night puts results on the site as soon as rows are added |
| 2026-11-21 | Field check also accepts the moment the bus is level with the stop (`pass_stop`, `field/0.2.0`), scored against the midpoint of the inferred arrival and departure | The first timings (2026-11-20, route 60, from on board) were taken at the stop, not 40 m either side; scoring them as departures would have added a spurious 7 s. Arrival and departure are 40 m either side of the stop, so their midpoint is the passing time at steady speed |
| 2026-11-21 | Field check (check 1) is a spot check on route 60, not about 40 timings at three or four timepoints (Davin's decision) | The observer rides only route 60. Its purpose is to show the tracking matches the street; the first five timings agreed within 2 to 7 s. Its limits are stated wherever the result is shown; checks 2 and 3 cover every route daily |
| 2026-11-21 | Remove the "experimental" label from stop events and on-time figures; show a plain note on what was checked (Davin's decision) | Checks 2 and 3 pass on every route daily and the route 60 spot check agreed within 2 to 7 s. The note says in-person checks so far cover route 60. `events/0.2.1` and `ontime/0.1.1` drop the `experimental` field from the output; inference is unchanged, and the version change rebuilds earlier days without it |
| 2026-11-21 | Monthly reports (`monthly/0.1.0`): when a month is complete, pool its days into `reports/YYYY-MM.json` and `.md`, add `SHA256SUMS-<release>.txt` to each of its Releases and use the report as their notes | Releases already fill day by day; a month-end report gives one citable summary per release and a checksum file anyone can verify downloads with. Counts are summed and shares recomputed from the sums, not averaged from daily shares. A missing last day delays the report seven days, after which missing days are listed |
| 2026-11-21 | Per-stop on-time breakdown keeping every deviation (`ontime/0.2.0`), a 28-day per-route summary (`ontime/recent.json`), and a route map file per schedule version (`maps/`) | Route pages need "usually N minutes late at this stop" over several days; medians cannot be pooled from daily medians, so the deviations are kept (about 1,000 whole numbers a day). The day files are rebuilt once for the new version; inference is unchanged |
| 2026-11-21 | Site map: route lines from Island Transit's own shapes drawn with Leaflet on OpenStreetMap tiles, with attribution | Free, no account or key; a map is the clearest way to show which routes run on time. The free county outlines available offline were too coarse (51 points for Whidbey Island). Tiles load in the visitor's browser; the site still works without them |
| 2026-11-21 | Collector `collect/0.3.0`: the prune job confirms each archived file with a one-byte ranged request and records every run in `prune_log`; a write the database refuses is tried once more; the scheduler waits longer for static downloads and prune runs | GitHub's file host answers the earlier size check (a HEAD request) with 401, so no day would ever have been pruned and the free database would have filled in about four weeks. Found the day before the first day became old enough to prune. What is fetched and stored is unchanged; a response that states no size no longer counts as confirmation |
| 2026-11-21 | Stop events `events/0.3.0`: tracking ends only after the bus reaches the point where arrival at the last stop is timed; a stop that cannot be placed on its shape in order within 150 m is `unplaced` and gets no time; each stop's offset from the shape is written; a trip that cannot be read no longer stops the day | A report landing 40 to 50 m short of the end of the shape ended tracking before the last-stop arrival was timed. One stop (West Beach at Norcliffe) could not be placed in order and was given the previous stop's time. Every stop in the current schedule lies within 19 m of its shape. On 2026-11-19 and 2026-11-20 observed timepoint events rose from 876 to 878 and from 2,001 to 2,009; on-time share from 59.9% to 60.0% and from 70.6% to 70.7% |
| 2026-11-21 | Timepoints follow the kind of day where a route prints separate timetables | Route 411C prints different stops for weekdays and Saturdays; before, a stop printed for either counted on both. Only 411C differs today |
| 2026-11-21 | Quality `quality/0.4.0`: a trip is observed only if a position carries its id within 30 minutes of its schedule; each position is counted once; an empty fetch is not also stale; trip gaps use one vehicle; off-route share is taken over the positions that were compared with the shape; uptime slots are centered on the scheduler's usual firing moment | A bus at a terminal shows its next trip's id long before the trip, and the same ids run every day, so an id seen at any hour proved nothing. On 2026-11-20 one trip had been counted as seen that way (trip coverage 97.36% to 97.07%). Off-route share had reports that were never compared with the shape in its total (4.0% to 4.3% and 3.4% to 3.6%). The other changes did not move either day's figures; they remove ways the figures could go wrong later |
| 2026-11-21 | One median and percentile for every stage (`pipeline/stats.py`, `ontime/0.3.0`) | On-time medians took the upper of the two middle values and the 28-day route tables used a third rule. Median deviation moved from 217.0 s to 216.3 s and from 180.7 s to 180.0 s |
| 2026-11-21 | Report the typical prediction miss (median absolute error) beside the mean, and count predictions off by more than 30 minutes | On 2026-11-20 about 2% of predictions made 5 minutes ahead were off by more than 30 minutes, some by 15 hours, although dated the right day. They took the mean miss from 4.3 minutes on 2026-11-19 to 9.2 minutes, while the typical miss was 2.4 minutes on both days. The site now shows the typical miss and states the share that is far off; both figures are published |
| 2026-11-21 | Island Transit's no-service holidays are listed in `reference/no-service-days.csv`; those days are flagged `service_expected: false` and left out of pooled figures. Replaces the decision of 2026-11-19 to report holidays only through Trillium's removals | Island Transit's website says no service runs on six holidays. Passio's calendar has no exceptions, so Thanksgiving would have shown every trip as scheduled and unobserved and pulled down the 28-day and monthly figures. The day is still archived and measured, and Trillium's removals are still recorded beside it |
| 2026-11-21 | A service day keeps the schedule version it was first pinned to; a day is rebuilt when its parsed tables are rebuilt or the checks' code version changes; crosswalk and map files are rebuilt when their code version changes | A later download could move an already published day to another version, and a rebuilt table left later stages pointing at a file that no longer existed |
| 2026-11-21 | Field check `field/0.3.0`: the 30-second target is judged from five timed moments; a loop trip is scored against the nearer visit to the stop | A target met on one or two timings says little. A loop trip visits its terminal twice and the two visits were confused |
| 2026-11-21 | Workflows install exact library versions (`constraints.txt`, Python 3.13) and actions pinned by commit; the nightly job publishes the `data` branch after every stage; the site build fails if the data is missing instead of deploying an empty site | A new release of a library could change a figure between two nightly runs with no change in this repository. A job that timed out lost every stage's manifest and repeated the same work next time |
| 2026-11-21 | Watchdog: an empty feed needs nine empty fetches in a row and is expected on no-service days; frozen vehicle timestamps, failed schedule downloads, prune errors and an unprocessed day are reported; one issue comment per change of state | One empty reply between two buses' reports is normal. The earlier check would have raised an alarm every half hour on Thanksgiving, and said nothing if positions froze or the prune job failed |
| 2026-11-21 | Site: one system font stack, no web fonts; charts carry text descriptions; table checkbox columns hidden; the site copies only the files its pages read | Two themes loaded two different web fonts from a third party. Charts had no text alternative. The whole `data` branch was being published a second time under the site |
| 2026-11-21 | Each nightly stage takes days it has never processed first, oldest first, and then the days it must rebuild, newest first, seven days per run | Every stage took the oldest pending day first. After a code version change with months of data, yesterday would have waited behind the whole backlog for several nights and the watchdog would have reported it as not processed. The figures do not change |
| 2026-11-21 | When two complete Passio downloads on one day differ, the day is pinned to the version whose scheduled trips the live feed reported that day (`pin/0.2.0`); a reviewed row in `reference/static-pin-overrides.csv` can replace a pin and is recorded with what it replaced; quality figures are rebuilt when a day's schedule version or timepoint list changes. Amends the pin rules of 2026-11-19 and 2026-11-21 | A day was pinned to its first complete download, made at 2:15 AM Pacific, and kept it for good. If Passio publishes the December 27, 2026 schedule later that morning, the day would have been measured against the old schedule permanently, with no way to correct it. No published day is affected: neither had downloads that disagreed |
| 2026-11-21 | The 28-day route tables pool only days measured against the printed timetable in effect on the last day (`routes/0.2.0`); `ontime/recent.json` says when a schedule change made the window start over | The window pooled every day by route and stop id, whatever the timetable. After the change on December 27, 2026, stops that were dropped would have stayed in a route's stop list for four weeks, and figures from two different timetables would have been added together. No published figure changes: every day so far uses the September timetable |
